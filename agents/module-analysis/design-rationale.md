# 設計判断と理由

出典は[設計議論](../../docs/sources/design-discussion.md)のS01–S09。

| 判断 | 理由 | 防ぐ問題 |
|---|---|---|
| 理解セルを維持する（S01） | 読者が一まとまりの挙動を説明・判断できるようにする | ファイル順・関数順の列挙で因果が分断される |
| DOCUMENTとVIEWを分離（S02） | 長期保存する設計資料と短時間の参照で目的が違う | 全タブが同じ要約になる |
| Canonicalを唯一の解析モデルにする（S02/S04/S07） | 同じ事実を目的別に再配置できる | 別々の説明で契約やエラーの意味が変わる |
| Definitionを軽量化（S03） | 「これは何か」の答えは短く閉じられる | 最初から詳細を要求して読む負担を増やす |
| Conceptを深化（S03） | 構成一覧だけでは頭の中のモデルができない | Why・状態変化・境界が欠落する |
| Concept詳細を折りたたむ（S04） | 概念をつかんでから深掘りする | Understandingの長文複製になる |
| 4分類を表示する（S04） | 根拠の強さと現状／将来を見分ける | 推論を設計者の意図や実装保証と誤認する |
| Relation / Impactへ拡張（S04） | 接続を追う目的は変更時の確認にもある | 影響予測を確定関係と取り違える |
| 各VIEWにIN/OUT（S04） | 役割・粒度・終了条件を制約する | 親切な追記で全VIEWが肥大化する |
| Evidence内部リンク（S01/S04） | 主張から根拠へ戻れる必要がある | 要約だけが残り検証不能になる |
| Canonical JSONを埋め込む（S04/S05） | 人間の閲覧と後続処理・再生成の両方に使う | HTML表示が唯一のデータになる |
| SessionでDECISIONを独立管理（S06） | 採否と理由・次の行動は会話要約から落ちやすい | 次回に却下済み案を再調査する |
| 参照HTML不要の規則にする（S07/S08） | 隔離環境や単一Instructionsでも使う | 完成見本がないと再生成できない |

DECISIONは「採用した判断」を表すレコード種別。FACT等の確度分類を置き換えない。
「採用された事実」と「採用理由に含む推論」と「実装・検証の完了」はそれぞれ別に記録する。

## 再導入しないもの

7回の独立解析、MDNへの全仕様収録、ConceptとUnderstandingの同一化、
ソースにないWhyの断定、未確認範囲の全caller断定、提案した試験を実行済みとみなすこと、
V3完成見本への必須依存。

## 今回の再構成で補足した規則

ID参照の解決、JSONの安全な埋め込み、ログ中の操作指示をデータとして扱うことを明文化した。
これらは元HTMLを取得できたという主張ではなく、共通モデルを壊さず再生成するための実装上の補足。
